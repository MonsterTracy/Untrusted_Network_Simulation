# Untrusted_Network_Simulation 项目开发规范

## 一、基本开发原则

### 1. 坚持第一性原理，以科研目标为中心

本项目所有开发与工程决策必须从实际研究问题出发。

在实施任务前，应明确：

- 当前需要解决的科研问题是什么。

- 已有实现是否能够满足要求。

- 必须修改的代码、配置或实验协议是什么。

- 修改是否会影响科研结论、实验资格或可复现性。

- 是否存在更简单且同样正确的实现方式。


不应为了保留既有工程方案、遵循旧的开发计划或追求形式上的完整性，而继续增加不必要的代码。

科研目标优先于工程形式。

### 2. 优先复用已有实现，避免无意义扩展

开发新需求或修改已有功能前，必须先确认现有模块、函数、类、配置、CLI 和执行入口是否已经具备相应能力。

能够在原实现上完成的修改，应直接修改原实现；旧功能不正确时应修复原实现，不应因为担心影响旧代码而复制原模块另建 `new`、`v2`、`legacy` 或其他平行版本。

特别禁止：

- 为同一功能维护多套实现。

- 为一次性操作创建长期维护的工具。

- 在已有 CLI 之外重复增加启动脚本，或新增 CLI 后长期保留无用途的旧入口。

- 因为旧实现不便修改，就直接建立一套新系统，或为新实验复制完整执行系统。

- 为保留旧代码不断叠加条件分支、同义配置或参数，增加实际运行路径的复杂性。

- 为普通修复增加不必要的兼容层、代理层或包装器。

- 为尚未出现的假设性需求提前设计复杂架构。


如果现有实现确实不满足科研需求，应明确其具体不足，再进行必要修改。

确有独立职责或科研协议要求时可以新增模块，但须说明必要性。正式对照实验、研究消融或冻结协议中的不同方法确需并行实现时，应明确各自职责和协议依赖，不得机械删除。

科研执行遵循**一条执行主线、最少必要门禁、验证按需分层、科研结果优先、旧逻辑及时退出**，不以新增协议和执行层级代替原位修复。

### 3. 只澄清影响正确性的关键不确定性

开发过程中出现不确定性时，应区分是否影响科研结果或不可逆操作。

对于不影响研究正确性的普通实现细节，允许依据项目既有规范作出合理选择。

对于以下问题，应先说明并取得用户决定：

- 研究目标或实验假设不明确。

- 模型、样本或评价协议需要改变。

- 可能影响冻结 Artifact。

- 涉及实验身份、Source Identity 或 GPU Qualification。

- 涉及新增用户可命名的文件、目录或实验标识。

- 涉及删除、覆盖、迁移或其他不可逆操作。用户已授权的 Mac 本地任务中，符合第4条条件的可恢复普通源码精简，无须为该范围内的删除重复审批；高风险删除仍须具体授权。


不要因普通细节反复中断任务，也不能在关键科研问题尚未明确时自行决定。

## 二、代码质量与最小实现原则

### 4. 不允许代码堆叠

项目代码应保持结构清晰、职责单一、易读、易懂、易维护。**优先考虑可读性，而不是追求代码简短。**

代码应让初次接触项目的开发者能够从上到下理解执行步骤及设计理由。这些是当前任务范围内的代码质量原则，不是强制重构命令。

修改已有功能或验证机制时，应核对旧实现的实际调用方和合同依赖。对于已被新实现完全取代、不再使用且无科研证据保护要求的普通代码与执行步骤，应在同一次变更中删除或合并，包括旧函数、重复分支、过期参数、无效包装器、重复入口，以及等效验证、重复资格检查、失效审批入口和不再使用的许可逻辑。不得仅为避免删除而长期保留无效实现；已经失效的遗留逻辑不应继续参与正式执行路径。

具体要求：

- **减少封装：** 仅对职责独立、确有复用价值，或独立封装能够明显改善正确性与理解成本的逻辑进行封装。避免过度拆分函数或为复用抽取大量辅助函数；正确、可验证且职责明确的已有封装，无需为减少函数数量而拆除。不为不存在的调用方长期保留多套接口。
- **减少修饰和包装：** 装饰器、类、继承、静态方法、属性包装和上下文管理器，仅在具有实际设计价值、正确性要求或资源安全意义时使用。不为体现设计模式或一次性研究验证添加不必要的抽象层。
- **减少嵌套：** 优先考虑提前返回（Early Return），减少不必要的多层 `if`、`try`、`with` 嵌套，让主要执行流程保持扁平；不得破坏异常处理、资源释放、事务边界或上下文管理语义。
- **优先使用直观语法：** 优先采用容易理解的 `if/else`、`for`、`try/except/finally`；谨慎使用复杂推导式、嵌套三元表达式、隐式技巧和过度简洁的语法。不一概禁止合理的语言特性，以实际可读性为判断依据。
- **避免过度压缩：** 宁可多写几行，也要清晰表达执行步骤和逻辑关系；不得为减少代码行数牺牲可读性、可调试性或维护性。
- **中文注释与 Docstring：** 新编写或实质修改的注释与 Docstring，原则上使用简洁、准确的中文，重点说明代码目的、设计原因、重要约束、关键逻辑及必须保留的特殊行为，不简单重复代码。外部 API、协议字段、标准术语、模型名称和必须保持原样的第三方内容继续使用正式名称；不为翻译注释批量修改无关历史源码。
- **命名清晰：** 变量、函数和类的名称应直观，使开发者无需反复跨文件跳转即可理解主要逻辑和对象职责；不得为统一风格随意改变已有公共接口、持久化字段或科研协议名称。
- **保持原有功能：** 结构优化应保持已有功能、业务逻辑、公共接口、异常处理语义和科研实验行为，不破坏历史 Artifact 与 Source Identity 验证合同，并遵守第6条的科研证据保护要求。任何可能改变行为的修改，都应单独说明修改内容及风险，先由用户决定，不能伪装成纯代码整理。
- **谨慎处理复杂机制：** 涉及异步执行、上下文传播、异常处理、资源释放、并发控制、文件锁与 GPU 锁、进程归属、数据完整性和安全、实验身份及科研证据验证时，正确性优先。已经实现并验证的资源锁、进程控制、异常恢复和并发机制，不得仅为降低复杂度而删除，也不得破坏已有安全性、确定性与恢复语义。
- **控制优化范围：** 不引入不必要的第三方依赖，不为形式上的架构整洁增加抽象层或开展与当前研究任务无关的大规模重构，不对无关源码自动格式化或清理。按第2条复用已有实现，避免为同一问题新增功能重叠文件或通过复制旧模块形成新模块，采用最小、清晰、正确且可维护的实现。

普通源码的版本追溯由 Git 历史承担：已提交代码可通过历史查看和恢复，已推送提交可作为 GitHub 远端历史来源，不应为保存旧版本长期维护重复文件或旧函数。未提交代码不能假定可从 GitHub 恢复，未推送的本地提交不能假定已由 GitHub 保存；不得覆盖其他尚未提交的工作，也不得为了代码清理改写 Git 历史。

在用户已授权的 Mac 本地开发任务范围内，上述普通源码精简仅在已确认无实际调用方和合同依赖、无科研证据保护要求且可通过 Git 历史恢复时，允许将删除作为最小正确修改的一部分；应保护未提交工作，并通过必要测试验证。涉及冻结 Artifact、研究数据、模型权重、服务器文件及历史证据、历史 Checkout、环境、持久化协议、外部接口或不可逆状态的删除，必须继续遵守原有规范并取得具体授权，源码已提交不构成删除这些对象的依据。本条不允许任意删除项目文件。

涉及替换原有功能的任务，完成时还应确认：原有功能已正确修改，被替代的普通旧代码不再参与执行，未无意新增重复实现，可直接清理的冗余分支或包装已处理，必要测试证明原功能与新功能符合要求。仅检查本次修改涉及的代码及直接依赖，不要求全仓库清理。

代码数量不是工作量的衡量标准。

应优先评价科研问题是否得到正确解决，以及实现是否具有可验证性与可维护性。

### 5. 禁止未经要求的兜底、降级和复杂防御逻辑

不得擅自引入：

- 自动降级到其他模型。

- 自动切换数据来源。

- 未经定义的失败重试。

- 静默忽略异常。

- 自动生成替代实验结果。

- 自动修复不匹配的 Artifact。

- 自动迁移目录或环境。

- 为通过测试而增加的特殊处理分支。

- 无明确研究必要性的强制门禁，例如多轮重复资格认证、多层审批和执行许可、合成推理门槛、每次运行全量扫描模型或数据、重复生成等效 Manifest、Receipt 或 Digest，以及无关的全仓库审计。


如果模型、数据或研究条件不满足要求，应明确报告原因。

发现验证风险时，应先定位具体错误及影响，确认现有机制是否覆盖，再优先原位修复、合并重复检查，并按第4条清理旧逻辑，以与风险相匹配的测试验证。只有现有机制确实不足、且新增门禁能防止重要错误时，才考虑增加强制步骤。

新增正式运行的强制检查前，须在正常开发说明中回答：

- 防止什么具体错误：错误类型、触发条件及实际影响，不能笼统归为“提高安全性”。
- 现有机制为什么不足：先检查是否可以复用、修改或合并已有验证。
- 增加多少执行成本：运行时间、GPU 占用、I/O、模型重新加载、维护成本及正式实验启动延迟；必要时说明为何必须在当前时机执行，而不能安排在首次准备、身份变化或运行结束时。

缺少充分理由的新增门禁，默认不增加；不为此另建审批表、验证注册表、管理脚本或专门审计系统。

不能删除正式研究协议中**明确规定并已经验证**的超时、重试、错误处理或安全机制。正式协议明确规定的其他检查与合同如需调整，须先评估研究影响并取得相应授权，不得以本规范为由直接删除；也不应无依据恢复已被合理删除的旧门禁。

区分协议要求与未经请求的工程扩展。

### 6. 精简代码不得破坏科研复现

普通开发代码与冻结科研证据必须区别对待。代码风格优化不得破坏科研正确性、冻结实验协议或证据完整性；已有源码、Artifact、Manifest、Receipt、Qualification 和 Admission 的历史验证语义必须保持。

科研正确性须以必要且充分的证据保证：数据、样本和任务身份正确，训练、推理及评价的信息边界合法且无 Gold 或未来信息泄漏，模型、Tokenizer 与推理协议符合研究定义，真实输出可靠保存，评价指标、结果及来源可追溯。不能用检查层数或协议数量代替这些性质，也不应默认将每项要求拆成独立的长期运行门禁。

以下内容原则上保持不可变：

- 已发布的 Canonical 数据。

- Collection Plan、Ledger 和 Manifest。

- 冻结样本及 Fold 分配。

- Model Checkpoint、Tokenizer 和模型身份。

- 已发布的实验配置及来源摘要。

- Deployment、Qualification、Admission。

- Prediction Seal。

- 已提交的正式实验结果与评价证据。


不允许因为当前 Mainline 已经包含相关源码，就直接删除原始实验 Checkout 或修改冻结 Artifact。

历史实现确实不再参与日常开发时，可以经过依赖核查后归档，但不得损害研究可追溯性。

## 三、项目结构、配置及命名规范

### 7. 使用已有项目结构和正式入口

项目以现有 Python 包、YAML/JSON 配置和正式 CLI 为基础。

默认规则：

- Python 模块负责算法、数据处理和执行逻辑。

- YAML/JSON 负责声明式配置。

- `configs/` 保存稳定配置和协议文件。

- `scripts/` 保存必要的研究分析或操作入口。

- `tests/` 保存对应测试。

- `docs/` 保存研究说明、执行协议及开发规范。

- 已有 `uns` CLI 的功能优先使用既有命令入口。


不应擅自引入新的配置管理框架、构建系统、实验调度平台或重复 CLI。

配置不应承担复杂程序逻辑，程序代码也不应重复硬编码可以配置的参数。

### 8. 新建目录和文件必须遵守用户命名决定

**所有新建的、可由开发者命名的项目目录和文件，应先由用户确定名称。**

包括但不限于：

- 项目源码目录。

- 研究模块及脚本。

- 配置文件。

- 新建测试文件。

- 研究文档。

- Candidate 根目录。

- 实验运行目录。

- 用户定义的实验标识。

- 需要长期维护的其他文件或目录。


AI 不得擅自添加以下后缀作为默认命名方式：

- `b2`、`v1`、`v2` 等无明确含义的编号。

- 随机字符串。

- 日期时间。

- Git Commit 简写。

- `new`、`final`、`final2` 等临时命名。


确实需要区分不同对象时，应先解释区别，再由用户确定名称。

**例外：** 已有程序或正式协议自动生成的内部文件名、内容摘要、Schema 版本和 Git Commit ID 不属于随意命名，不得为了遵守本条而擅自修改。

已经冻结的历史 Artifact 也不因新命名规范而自动改名。

若用户已明确批准某一命名规则，可以按该规则执行，不需要重复询问。

### 9. 优先复用现有环境和工具

不得为了普通代码修改、测试或研究分析而默认新建：

- Conda 环境。

- Python 虚拟环境。

- Git Worktree。

- Git 分支。

- 重复的源码 Checkout。

- 临时项目副本。


使用已有环境前，应确认其适用的 Python 版本、依赖和源码绑定。

终端命令应简短、可阅读、可复制。

不应通过长篇终端 heredoc 临时拼接需要长期维护的程序代码。

如果修改属于长期项目功能，应在现有或经用户命名批准的源码文件中实现。

## 四、科研建模和实验管理原则

### 10. 明确项目研究模块的职责

本项目主要涉及以下研究方向：

**狼人杀模拟与 Canonical 数据**

负责真实游戏轨迹、规范事件、PRE 状态、数据来源及数据发布。

**Observer-specific Theory of Mind（观察者特定心理理论）**

负责从合法观察者信息出发，建立其对其他玩家状态和意图的认知估计。

**Decision-Theoretic Rough Sets（三支决策粗糙集）**

负责条件概率、损失函数、决策阈值及 POS、BND、NEG 三域决策。

**三支决策发言策略**

负责将三域决策映射为合法发言策略，并在真实游戏约束下验证。

**TomBaseline**

负责使用通用大语言模型构建 ToM 对照基线，形成可以比较的预测结果及研究评价。

这些模块属于同一个项目，但其输入、输出、资格和实验结论不能混淆。

### 11. 严格区分不同实验阶段

以下阶段具有不同的验证含义：

1. 源码开发与静态检查。

2. CPU 单元测试。

3. Mock、Stub 或合成输入验证。

4. Tokenizer 和模型资产核验。

5. CPU Deployment 准备。

6. Source Identity 核验。

7. GPU Qualification。

8. Admission。

9. 正式模型推理与实验运行。

10. 实验统计分析与结果报告。

这些阶段用于区分证据含义，不代表每项科研任务均须增设全部独立门禁或每次运行重走全链。真实模型服务可运行、已完成真实推理、正式预测结果完整与科研效果得到验证，应分别判定；工程认证层数不能替代科研进展。

本地精简或规范修订不自动授予新运行版本 Ubuntu GPU 资格，执行性能改善须有实测证据。


不得将前一个阶段的成功直接解释为后一个阶段已经完成。

特别是：

- CPU 测试成功不代表 GPU Qualification 通过。

- Mock Seal 不代表真实 Prediction Seal。

- Deployment 存在不代表 Admission 有效。

- 源码可以导入不代表真实实验成功。

- 算法在给定概率和成本下最优，不代表动态策略最优或游戏胜率提高。


### 12. 保持科研协议及数据身份稳定

已有研究明确规定的以下内容不得随意更改：

- PRE 和 POST 信息边界。

- Observer-specific 可见信息。

- 游戏和观察者身份。

- 事件及标签定义。

- 训练、验证和测试划分。

- Selection 和 Cohort。

- Fold 分配。

- LossSpec 和评价指标。

- 随机种子与预设实验条件。

- Source、Manifest、Digest 等身份信息。


如果新的研究目标确实需要改变上述内容，必须明确提出新的实验定义。

不得通过覆盖旧 Artifact 或重写旧 Manifest 来改变既有研究结论。

### 13. 严格区分方法能力与实证证据

研究报告中应明确区分：

- 理论推导。

- 算法实现。

- 合成数据验证。

- 历史数据统计。

- 离线预测表现。

- 真实游戏内执行效果。

- 因果效果或胜率改善证据。

### 18. 测试必须与实际风险匹配

优先顺序为：

1. 相关函数或模块测试。

2. 对应集成测试。

3. 受影响的依赖闭包检查。

4. 必要的跨模块回归。

5. 正式提交或实验所需的完整验收。

验证按执行时机分层：

- **首次准备或相关身份变化时：** 核验模型资产完整性、Tokenizer、环境依赖、固定数据和配置等成本较高的项目。
- **运行启动或危险操作前：** 轻量核对当前服务身份、PID、Socket、GPU 互斥与资源锁正确性、必要的模型配置，防止误连接或误停止其他服务。
- **运行过程中：** 检查请求状态、真实输出持久化、重复执行防护、未知执行结果的安全处理、错误处理、断点恢复、原子写入及结果完整性。
- **运行结束时：** 核验结果覆盖率、完整性、身份对应关系及正式评价所需证据。

是否重新验证，由相关输入、身份、运行状态是否变化及错误影响决定；可安全复用的已核验证据不重复计算，不因检查存在而在每次执行时完整重跑。复用不得弱化正式协议所需的科研验证、运行安全或冻结证据核验，安全性质应优先由现有的最小正确实现保证。


不应为普通局部修改重复扫描整个仓库。

也不能为了减少测试而跳过关键风险。

实验执行效率是正式设计约束：在符合科研协议和安全要求的前提下，缩短启动任务到产生第一条有效结果的时间，避免不必要的模型重复加载、服务重启、昂贵的重复验证及不产生科研数据的串行准备步骤，优先持续可靠地保存真实输出。明显耗时的新增步骤，应按真实测量和具体风险评估收益是否足以支持成本；不设置脱离实际条件的统一耗时上限，也不得为追求形式上的验证完整性无限延迟实验。

不得通过 Mock 或合成数据测试代替真实物理环境资格。

为便于区分研究方向、追踪任务进展和检索历史对话，Codex 对话采用**研究方向固定字母、同方向新对话递增数字**的命名方式。

**统一格式：**

`字母+两位数字-研究方向｜具体任务`

其中，使用 A–Z 共 26 个英文字母为项目中的研究方向分配前缀，每个研究方向使用一个稳定的字母，数字为该方向内部 01–99 的两位编号。

具体字母优先沿用已有研究方向映射，不预设 TomBaseline 必须为 A 或三支决策必须为 B。不同研究方向使用不同字母，除非用户明确要求重新规划。

**格式示例（字母分配仅作示例，实际沿用已有映射）：**

- `A01-TomBaseline｜多模型基线开发`
- `A02-TomBaseline｜实验部署与验证`
- `B01-三支决策｜损失函数建模`
- `B02-三支决策｜发言策略开发`

**具体执行规则：**

1. **研究方向与序号分配：** 某研究方向首次需要编号时，检查当前项目实际可访问的已有对话命名，优先沿用该方向已经建立的字母映射。如果该方向此前没有分配字母，则按 A、B、C……Z 的顺序，选择尚未使用的最靠前字母，从 01 开始编号。同一研究方向下新建对话时，始终沿用该方向原有字母，只递增数字序号。数字在各研究方向内部独立连续递增，根据该方向已有最大编号顺延，不与历史编号重复，也不因中间缺号而重新使用旧编号。信息不完整时按第 5 项处理，不将“未能获取”视为“尚未分配”。
2. **历史标题与映射保护：** 保留既有对话标题、编号和字母映射，不因规范修改而批量重新命名历史对话，也不因删除或归档对话而自动重新编号。
3. **首次命名时机：** 新建 Codex 对话后，在研究任务首次明确时，根据研究方向与序号分配规则生成或设置一次标题，准确体现该任务。如果首次发言已经明确研究任务，应在首次响应时完成命名；如果任务尚不明确，则在任务首次明确时命名。
4. **标题与编号稳定：** 同一对话后续所有发言，默认沿用已经确定的标题和编号，不重新分配序号、不自动更名，也不反复输出建议标题。即使进入代码修复、测试、验收或研究的下一阶段，只要仍属于同一对话，标题就保持不变。只有用户明确要求重命名时，才允许修改已有对话标题；若仅修改任务描述，原编号原则上保持不变。不得因重命名而擅自改变其他对话编号。
5. **映射与编号信息不完整：** 不得假装已经查看无法访问的对话标题，也不得猜测已占用的字母或序号。应优先利用实际可访问的项目对话清单、用户提供的历史编号或当前对话信息。无法可靠取得完整历史时，可以根据已有信息提出明确标注为“待确认”的命名建议，不得声称其已被验证为全项目唯一编号；必要时由用户提供已有映射。信息暂时不足不应阻碍其他独立科研任务；映射或编号冲突影响实际命名时，向用户简短确认。不要因标题编号问题反复询问、重复命名或开展与科研无关的长时间检查。
6. **避免无意义拆分：** 不得为了增加编号而将一个连续研究任务拆成多个对话。
7. **实际命名能力：** 首次命名时，具备直接设置标题的能力则按规范设置一次；不具备该能力则只提供一次建议标题，供用户手动设置，且不得声称已经自动完成命名或重命名。
